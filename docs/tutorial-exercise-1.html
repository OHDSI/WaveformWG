OHDSI Waveform WG

Exercise 1: Explore WFDB recordings

Goal

Open a WFDB record, convert its stored integers to physical units, and decide what has to come from outside the file before it can be used in an OMOP analysis.

Background

WFDB is the format used by PhysioNet. A record is a small text header (.hea) plus one or more binary signal files (.dat). The header says how to read the bytes: sampling frequency, number of samples, one line per channel with its format, gain, baseline and label, and optionally the acquisition date and time. Signals are stored as integers (digital values); the gain converts them to physical units such as millivolts.

The header is deliberately free of patient identifiers. That is good for privacy, but it means the file cannot tell you whose ECG it is, or which hospital encounter it belongs to. In real life the link comes from the export system, and it has to be carried into the OMOP tables.

Learning Outcomes

  1. Read a WFDB header and signal with the wfdb Python package
  2. Convert digital samples to millivolts and explain the role of gain and baseline
  3. Check a signal for internal consistency (Einthoven’s relation)
  4. List the facts the Waveform Extension needs that the file does not contain
  5. Recognize a poor-quality recording and say how you would record that

Materials

  • The records in data/wfdb/ and the export list data/source/ecg_manifest.csv
  • Reference solution: tutorial/solutions/ex1_explore_wfdb.py

Steps

Run the code from syntheticData/qtc.

1.1 Read the header

import wfdb
hdr = wfdb.rdheader("data/wfdb/A0000001")
print(hdr.fs, hdr.sig_len, hdr.sig_name, hdr.units, hdr.adc_gain, hdr.baseline)
print(hdr.base_date, hdr.base_time, hdr.comments)

Also open data/wfdb/A0000001.hea in a text editor and match each field to what you printed.

Question 1.1. How long is the recording in seconds? How many bytes should the .dat file have (16-bit samples)? Check with ls -l.

Answer 2,500 samples at 250 Hz is 10 s. Three channels x 2,500 samples x 2 bytes = 15,000 bytes, and the .dat file is exactly that (the header is a few hundred bytes). A header-versus-file size check is a cheap integrity test for an ETL.

1.2 Digital versus physical

rec = wfdb.rdrecord("data/wfdb/A0000001")                          # physical (mV)
raw = wfdb.rdrecord("data/wfdb/A0000001", physical=False).d_signal  # stored integers
print(raw[:3, 1], rec.p_signal[:3, 1])

Question 1.2. The first three lead II integers are 24, 11 and 2. What are they in millivolts? What would go wrong if an ETL recorded the gain as 200 instead of 1000?

Answer physical = (digital - baseline) / gain, so 24 / 1000 = 0.024 mV, 11 / 1000 = 0.011 mV and 2 / 1000 = 0.002 mV. With a wrong gain of 200 every amplitude would be five times too large (R waves of about 6 mV instead of 1.2 mV). Interval measures such as QT would survive, but any amplitude-based feature would not. That is why the extension stores resolution as channel metadata: the gain is part of the provenance of every feature.

1.3 Is the signal internally consistent?

Lead III should equal lead II minus lead I (Einthoven’s relation).

import numpy as np
mv = rec.p_signal
print(np.abs(mv[:, 2] - (mv[:, 1] - mv[:, 0])).max())

Question 1.3. Why is the difference not exactly zero in a real recording, and why is it (almost) zero here?

Answer In a real ECG, leads I, II and III are derived from the same electrodes, so the relation holds up to amplifier differences and quantization; a large violation signals a lead-off, swapped electrodes or a processing error, which makes this a useful automatic quality check. Here lead III was computed from the other two in integer arithmetic, so the difference is zero up to floating point rounding.

1.4 Plot it

import matplotlib.pyplot as plt
wfdb.plot_wfdb(record=rec, title="A0000001", figsize=(10, 5))

Find the R peaks (the tall spikes) and count them. Estimate the heart rate as beats per minute from the count and the duration. Then compare with the true_hr_bpm column for A0000001 in the answer key.

1.5 Who is this?

import pandas as pd
manifest = pd.read_csv("data/source/ecg_manifest.csv")
print(manifest[manifest.accession == "A0000001"].T)

Question 1.5. List everything the Waveform Extension needs for this recording that is not in the .hea file, and where you would get each item.

Answer Four things. First, the patient: person_id, resolved from the MRN in the export manifest through PERSON.person_source_value. Second, the clinical context: visit_occurrence_id, resolved from the encounter id through VISIT_OCCURRENCE.visit_source_value. Third, the meaning of the labels: channel names such as “II” become standard channel_concept_id values from the vocabulary. Fourth, where the file lives now (waveform_target_file_uri) and where it came from (waveform_source_file_uri). The acquisition time is in the header here, but real headers often omit it or carry a local-time/time zone ambiguity, so cross-check it against the manifest, which Exercise 2 does.

1.6 Clean versus noisy

Records A0000001 and A0000002 differ in quality. Plot both, then measure how noisy each is by taking the standard deviation of the signal after subtracting a short moving average:

s = wfdb.rdrecord("data/wfdb/A0000002").p_signal[:, 1]
hf = s - np.convolve(s, np.ones(5) / 5, mode="same")
print(hf.std())

Question 1.6. Which record is noisy? Where in the Waveform Extension would you record that, so an analyst can exclude it later without re-reading the signal?

Answer A0000002 has a high-frequency SD of about 0.17 mV against about 0.013 mV for A0000001. The extension has two natural places: a waveform_channel_metadata row (a signal-quality metadata type with value_as_concept_id = Low signal quality, as the existing synthetic set does) or a quality flag on the waveform_feature rows derived from the record. This tutorial uses the second, because it travels with the numbers an analyst actually uses (Exercise 3).
